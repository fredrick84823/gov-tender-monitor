# 實驗：openfun API vs 官網爬蟲，哪一邊的資料更完整、更可信？

**日期**：2026-09-09　**執行**：`scripts/experiment-scraper.js`
**資料日**：2026-08-17（`web/data/demo-data.json` 的 `20260817`）

> 這個實驗是**事後補做**的。專案一開始就選了 g0v/openfun 鏡像 API（`config/rules.json`
> 的 `source.baseUrl`），當時沒有做實驗。下面是實際量到的證據，包含對爬蟲有利的部分。

---

## 問題

同一批標案，openfun 鏡像 API 與直接爬官網（`https://web.pcc.gov.tw`），哪一邊給出更完整、更可信的資料，代價各是多少？

### API 側

沿用 `src/pcc-client.js` 的 `createPccClient()`（含 1 req/s 序列化、瀏覽器 User-Agent、
429 盲目退避）打 `/api/tender?unit_id=…&job_number=…`，再用 `src/enrich.js` 的
`pickAnnouncement()` 挑出對應 filename 的那筆公告，`field()` 以 `區塊:欄位` 尾段取值。

為了跟爬蟲公平比較延遲，額外注入一層計時 `fetch`，把「純 HTTP 往返」與「含 throttle 排隊」分開量。

### 爬蟲側

入口 `https://web.pcc.gov.tw/prkms/tender/common/noticeDate/redirectPublic?ds=…&fn=….xml`
（只需 list 的 `date` + `filename`，不必先打 API），手動跟 303 以記錄整條轉址鏈。
HTML 用 regex 解析，不加任何依賴 —— **明確標記為實驗等級，不是生產解析**。
序列化、約 1 req/s、帶瀏覽器 User-Agent。

### 比較的 10 個欄位

標的分類、採購性質、預算金額、預算金額是否公開、截止投標、公告日、招標方式、機關聯絡人、履約地點、履約期限

- 缺的都是那 2 筆 PPW，**兩邊一樣缺** —— 這類公告的來源本身就沒有這些欄位（見「意外發現」）。
- 84 組「兩邊都有值」的配對中，**語意差異 0 筆**。

  （`matchedExactAnnouncement: true`），兩筆更正公告的欄位值與官網頁面一致。

### 三、只有一邊有的欄位

**API 獨有：**

| 欄位 | 說明 |
|---|---|
| `fetched_at` | 鏡像的抓取時間戳（例：`2026-08-17T01:29:41+08:00`）。官網頁面上沒有這個資訊，是**只有 API 才給得出的 provenance** |
| `url` / `pkPmsMain` | 官網原文連結與內部主鍵（範本超連結用的就是這個） |
| 整案公告史 | 一次 `/api/tender` 回傳該案所有公告版本：本次樣本 1、2、4、7 筆不等（TIQ-11-71094130 有 **7 筆**）。官網詳細頁一頁只有一個版本，要看歷史得再打 `thdTenderHisResult?caseNo=…&tenderSq=04` 這種一版一頁的路徑 |
| 巢狀子欄位 | API 把巢狀表格攤平成 `領投開標:是否提供電子領標:機關文件費(機關實收)`、`系統使用費`、`總計`、`廠商應附具之基本資格證明文件或物品`、`疑義、異議受理單位` 等。同一頁我的 regex parser 只解出 65-66 個標籤，API 有 79-88 個 key，**API-only 有 16-22 個** |

**爬蟲獨有：本次樣本 0 個。**

唯一「只有官網有」的兩個標籤 —— `本案完成後所應達到之功能、效益、標準、品質或特性` 與
`身心障礙福利機構團體或庇護工場生產物品及服務` —— 8/8 筆的值都是空字串
（後者只有 `項目：` `分類：` 兩個空白 label）。官網把空欄位也畫出來，API 丟掉空值，
所以這是「渲染差異」不是「資料差異」。其餘看似獨有的 `是否適用條約或協定之採購`、
`疑義、異議、申訴及檢舉受理單位` 都是群組標題，API 用前綴表達了。

### 四、值的格式：`標的分類` 8/8 筆不同，而且會打壞現有 parser

```
API   : "勞務類871-廣告服務"
爬蟲  : "勞務類\n \n 871 - 廣告服務"      （官網原始 HTML 是 勞務類<br>871 - 廣告服務）
```

實測 `src/select.js` 的 `parseCategory()`：

```
parseCategory('勞務類871-廣告服務')      → { nature:'勞務類', code:'871', name:'廣告服務' }
parseCategory('勞務類\n \n 871 - 廣告服務') → null
```

改走爬蟲，`select()` 的路 A（標的分類命中）會整條失效，得再寫一層正規化。

### 五、延遲

| | n | min | median | max | mean |
|---|---|---|---|---|---|
| API 純 HTTP | 10 | 279 | 283 | 613 | 316 ms |
| API 含 1 req/s 排隊 | 10 | 621 | 1,287 | 1,292 | 1,220 ms |
| 爬蟲（整條 303 鏈，2-3 hop） | 10 | 274 | 1,834 | 4,916 | 2,427 ms |

- 跨源要看「純 HTTP」對「整條 303 鏈」：中位數 **283 ms vs 1,834 ms，約 6.5 倍**。
- 爬蟲的數字沒有包含腳本自己的 1,100 ms 禮貌間隔，也沒有包含解驗證碼的時間。
- 傳輸量：API JSON 每案 3,257 / 18,835 / 66,581 bytes（PPW / 一般 / 7 版公告史）；
  官網詳細頁 HTML 每頁 113,753-121,885 bytes，驗證碼頁 43,749-43,760 bytes。
  同一筆 TIQ-3-71094270：API 18,835 bytes vs HTML 120,626 bytes，**約 6.4 倍**。

### 六、程式量與脆弱點

以本腳本實測行數（不含空行與註解）：

| | 行數 |
|---|---|
| API 端取值 `fromApiDetail()` | **7** |
| API 端整區（含 client 包裝、計時） | 54 |
| 爬蟲端純解析（`stripTags` 10 + `parseLabelValuePairs` 23 + `fromHtmlPairs` 10 + `classifyPage` 7） | **50** |
| 爬蟲端整區（再加 `fetchOfficialPage` 48 行手動跟轉址） | 144 |

取同樣 10 個欄位：**7 行 vs 98 行**（50 行解析 + 48 行轉址處理），而且 API 端那 7 行是靠
`src/enrich.js` 既有的 `field()` 做掉大部分工作。**爬蟲端還完全沒有寫** cookie jar、
驗證碼流程、兩代頁面偵測。

會弄壞爬蟲的東西，實測到的：

1. **同一站有兩代頁面，三組 class 慣例。** 標籤/值配對完全綁在純呈現用的 class 名稱上：

   | 頁面 | 標籤 cell | 值 cell |
   |---|---|---|
   | 二代 `/prkms/…/viewDetail` | `class="T11b"` | `class="newstop"` |
   | 三代 `/tps/…/historyTenderDetail` 機關資料區 | `class="tbg_1"` | `class="tbg_2"` |
   | 三代 同頁 採購/招標資料區 | `class="tbg_4"` | `class="tbg_4R"` |

   官網改一次版型，這段全滅。第一版 parser 只寫了 `T11b/newstop`，套到三代頁面解出 **0 個欄位**。

2. **值裡有 `<br>`。** `標的分類` 就是這樣壞的（見上）。

3. **巢狀表格。** 電子領標費用、疑義異議受理單位是表格中的表格，扁平的 label→value 掃描解不到，
   這是爬蟲比 API 少 16-22 個 key 的原因。

4. **反爬蟲措施 —— 撞到了兩種：**
   - **撲克牌驗證碼**（`驗證碼檢核`）：招標類詳細頁無條件觸發。冷抓 5/5 撞牆。
     圖片配對題，需要視覺推理；表單帶 `_csrf` 與一次性 `id`。
   - **配額**：手動解一次後，接下來的詳細頁可以連看 **6-7 頁**，然後牆回來
     （第一次解：解完後連續 6 頁 content，第 7 頁撞牆；第二次解：7 頁後撞牆）。
     以 20260817 的 35 筆入選量估，每天要解 **5-6 次**驗證碼。
   - **配額不在 cookie 裡**：解完之後用完全不帶 cookie 的 Node `fetch` 仍拿到內容，
     所以額度是伺服器端按 client（IP）記的。也就是說換 session 逃不掉。
   - **WAF 直接封 headless 瀏覽器**：用 Playwright（headless Chrome）開同樣的 URL，拿到的是
     `Web Page Blocked! … Attack ID: 20000051`，連 `/prkms/tender/common/basic/indexTenderBasic`
     首頁都被封。同一時間、同一個 IP 的 curl 仍然通（拿到驗證碼頁，不是 WAF 頁）。
     **所以「用真瀏覽器自動解驗證碼」這條路，在瀏覽器指紋這一層就先被擋掉了。**

5. **不需要 JS 渲染。** 這一項對爬蟲有利：詳細頁的欄位都在 server-side render 的 HTML 裡，
   沒有 XHR 補資料，不需要跑 JS。編碼也乾淨（UTF-8，`Content-Type` 有帶 charset）。

## 意外發現

1. **「公開徵求廠商提供參考資料公告」不是 API 的鍋，是來源本身就這樣。**
   ADR 003 的推論是對的但理由要修正：這類公告 API 只給 19 個 key，我原本假設是鏡像掉了欄位。
   實際比對官網頁面（PPW 路徑不撞牆，可以直接驗證）：官網解出 16 個標籤，
   **API 是官網的嚴格超集**，多出來的只有 `type`、`url`、`fetched_at` 三個 meta。
   兩邊都沒有標的分類、沒有預算、沒有截止投標 —— 這類公告在法定格式上就沒有這些欄位。
   換去爬官網不會多拿到任何一格。

2. **官網對這類公告反而給了更豐富的敘述欄位，而 API 一字不漏地都有。**
   `內容摘要`、`附加說明`、`公開徵求期間`、`是否提供公開徵求說明文件`、`電子郵件信箱`
   —— 這些都在 API 裡，值完全一致（含全形括號與換行）。

3. **驗證碼是可解的，而且解一次能看好幾頁。** 原本以為是死路；實測是「收過路費」的設計。
   這改變了結論的性質：爬蟲不是不可能，是**每天要有人（或一個視覺模型）付 5-6 次過路費**。
   而繞過一個站方刻意裝上的存取控制，是另一回事，不只是工程問題。

4. **WAF 對 headless 瀏覽器比對 curl 更嚴格。** 直覺上「用真瀏覽器比較不容易被封」，實測相反。

5. **API 的 `fetched_at` 是唯一一個「官網沒有、鏡像才有」的欄位**，而它剛好是資料可信度的關鍵：
   它告訴你這筆資料是什麼時候從官網抓的。爬蟲雖然是第一手，但也不會告訴你頁面上的值
   是哪個版本 —— 得自己記時間戳。

## 結論

**維持 openfun API。分軸來看：**

| 軸 | 贏家 | 證據 |
|---|---|---|
| 欄位完整度（可及的情況下） | **平手** | 10 欄位 8/10 vs 8/10；84 組配對語意差異 0 筆 |
| 欄位完整度（實際可及性） | **API** | 冷啟動直抓官網 10 筆只有 2 筆拿到（2/10），其餘撞驗證碼牆 |
| 結構深度 | **API** | 79-88 key vs 65-66 標籤；巢狀子欄位 API-only 16-22 個 |
| 資料可用格式 | **API** | `標的分類` 8/8 筆格式不同，爬蟲那種寫法會讓 `parseCategory()` 回 null |
| 資料 provenance | **API** | `fetched_at` 是官網頁面上不存在的資訊 |
| 一次取回公告史 | **API** | 一次 call 拿 1-7 個版本；官網一頁一版本 |
| 延遲 | **API** | 中位數 283 ms vs 1,834 ms（6.5 倍）；傳輸量 6.4 倍 |
| 程式量 / 脆弱度 | **API** | 7 行 vs 98 行；爬蟲綁在 3 組純呈現 class 名稱上，還沒算 cookie 與驗證碼流程 |
| 無中介、第一手 | **爬蟲** | 官網是法定唯一來源，不依賴第三方鏡像的存活與正確性 |
| 不需要 JS 渲染 | **平手** | 官網詳細頁是 server-side render，這條沒有加分給誰 |
| 自動化可行性 | **API** | 官網每 6-7 頁一次圖形驗證碼（每天 5-6 次），額度按 IP 記，headless 瀏覽器被 WAF 直接封 |

**爬蟲唯一真正贏的一軸是「第一手」。** 這一軸的代價（每天 5-6 次視覺驗證碼、
綁在 class 名稱上的 98 行解析、6.5 倍延遲）遠大於它換來的東西 —— 因為在資料內容上，
本次樣本量到的差異是 **0**。API 沒有丟掉任何一格，反而多給了 provenance 與公告史。

**建議的補強**（不改資料源）：既然 API 是鏡像，就要能偵測鏡像失效。
`fetched_at` 已經給了工具 —— 若某天的 `fetched_at` 明顯落後於資料日，就該告警。
另外 `redirectPublic` 連結（`select.js` 的 `tenderUrlFor()`）本來就會出現在報表裡，
客戶點進去看到的就是官網原文，這條人工核對路徑不受本實驗影響。

## 這個實驗沒有回答的問題

1. **樣本只有 10 筆、只有一天（20260817）。** 不能推論 API 對所有公告類型、所有機關都是超集。
   本次沒有涵蓋的類型：決標公告、無法決標公告、招標文件公開閱覽公告資料公告（規格白名單裡有）。
2. **沒有長期穩定度資料。** 完全沒測：鏡像會不會某天沒更新、落後幾小時、
   或某段時間整批缺公告。這是選鏡像最大的風險，而本實驗一次都沒碰。
3. **沒有量「鏡像正確性」，只量了「鏡像與官網一致性」。** 兩邊都可能同時錯（例如機關自己填錯）。
4. **驗證碼配額只觀察到 2 次解題（6 頁與 7 頁）。** 「6-7 頁」是 n=2 的觀察，
   不知道配額是固定值、時間窗、還是隨負載變動。
5. **沒測 API token。** `createPccClient` 支援 openfun token（免速率限制），
   本實驗全程走匿名 1 req/s。有 token 的延遲與吞吐沒有量。
6. **WAF 封 headless 瀏覽器只試了 Playwright headless Chrome。** 沒試 headed、
   沒試改指紋、沒試真實使用者的瀏覽器。所以只能說「這個組合被封」，
   不能說「所有瀏覽器自動化都被封」。
7. **沒有評估法律與服務條款面。** 「解驗證碼」在工程上可行，但它是站方刻意裝上的存取控制，
   要不要繞過不是這份實驗能決定的。本實驗只手動解了 2 次以取得比對用的 HTML，
   腳本本身不含破解程式。
