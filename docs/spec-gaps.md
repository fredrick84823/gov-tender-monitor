# 規格落差清單

實作過程中，比對三份來源後發現的矛盾與缺口：

- **A** — 客戶需求規格 `docs/requirements.md`（Pages 定案版）
- **B** — 客戶提供的實際輸出範本 `gov_tenders_20260817.xlsx`
- **C** — 政府採購網 API 的實測行為

處理原則：**B 優先於 A**（範本是客戶手上真正在用的東西），**C 是事實**（API 做不到的，規格再怎麼寫也沒用）。

---

## 一、已在實作中處理

### 1. 版型：範本與規格完全不同 〔A ↔ B〕

| 項目 | A 規格說 | B 範本實際 | 採用 |
|---|---|---|---|
| 分頁 | 一大類一分頁 | **單一分頁** `標案日報 YYYYMMDD` | B |
| 每筆列數 | 兩列一筆 | **一列一筆** | B |
| 分區依據 | 標的分類大類 | **搜尋路徑**（大類搜尋 + A/B/C/D 組關鍵字） | B |
| 命中標示 | 四色色碼 | **無色碼**，改用分區歸屬；底色只是斑馬紋 | B |
| 欄位 | 規格自己列了兩組互相矛盾的欄位 | 公告日期／機關名稱／標案名稱／截止投標／預算金額／標的分類 | B |

規格第四節內部就自相矛盾：「版型」句列的是 機關／案號／招標方式／採購性質／公告日／截止日，「欄位」句列的是 標案名稱／機關／標的分類／截止投標／預算。兩者都不等於範本。**已改以範本為準。**

### 2. 去重鍵是錯的 〔A ↔ C〕

規格寫 `unit_id + job_number` 聯集去重。實測：**這是「案件」鍵，不是「公告」鍵**——原公告與更正公告共用同一組值。照規格實作會把每一筆更正公告都當成重複丟掉，客戶因此收不到截止日延期之類的關鍵異動。

**已改用 `filename`**（公告唯一鍵，如 `TIQ-11-71107895` / `TIQ-12-71107895`，尾碼相同、序號遞增）。更正公告照收，標案名稱前綴 `【更正】`。

### 3. 有一種指定的公告類型，API 給不出任何欄位 〔A ↔ C〕

規格收錄的 10 種公告裡，「公開徵求廠商提供參考資料公告」的 `brief.category` 是 `null`，細查回來也只有 15–18 個欄位——**沒有標的分類、沒有預算、沒有截止投標**。

影響：這類公告路 A 永遠篩不到（只能靠路 B 關鍵字撈），且無從判定是否為勞務類。若嚴格套用「限勞務類」會把整類丟掉，等於漏報。

**已處理**：分類為 `null` 時放行關鍵字路徑，三個欄位如實印「未公開」。

### 4. 排除清單會靜默誤殺 〔A 的設計缺口〕

38 條排除詞是**對整個標題做字串包含比對**，但這些詞描述的是「採購標的」。標題裡常同時出現場地名與真正的標的，例如：

> 台中市OO**活動中心**啟用晚會宣傳影片製作

被第 13 條「活動中心」擋下——但這正是客戶要的媒體製作案。規格第八節自承這串清單是「客戶回饋『這件不該出現』就加一條」累積出來的，**卻沒有反方向的回饋路徑**：被誤殺的案子無聲消失，客戶永遠不會發現，也就永遠不會反映。

**已處理**：Excel 增加「已排除」分區（不在客戶範本內，是本專案刻意加的），列出每一筆被哪一條詞擋下、原本會命中哪幾組，並保留官網連結供抽查。依排除詞分組排序，同一條詞的受害者排在一起，一眼就能判斷某條詞是不是訂得太寬。

### 5. 預算與日期的資料誠實 〔A ↔ C〕

- `預算金額` 是字串 `"1,000,000元"`，不是數字。
- `預算金額是否公開` 是**多行字串** `"否\n預算金額涉及商業機密"`，不能用 `=== "否"` 比對。
- 民國年需轉西元（範本的日期欄一律是 `2026-08-21 17:00`）。

**已處理**：未公開一律印「未公開」，轉換失敗回 `null` 再印「未公開」，任何情況都不補 0、不猜值。

### 6. API base URL 已搬遷 〔C〕

`pcc.g0v.ronny.tw` 現在 301 導向 `pcc-api.openfun.app`，**且會吃掉 path**。已改用新網址。

### 7. 「與 ad-report byte-identical」做不到 〔A〕

xlsx 是 zip，內含建置時間戳與 docProps，逐位元組相同在實務上不可能。且 `tagtoo_xlsx.js` 不在本 repo。**已改為直接實作範本樣式**，並在程式碼留下 TODO 標記日後抽換。建議與客戶把驗收條件改寫為「共用同一套樣式模組，外觀一致」。

## 二、需要客戶確認，尚未決定

### 8. 規格缺少第三節

`docs/requirements.md` 章節是 一 → 二 → **四** → 五 → 六 → 七 → 八。已確認**原始 Pages 檔本身就跳號**（全文只有一段連續文字流，非轉檔遺漏）。`send_when_empty = True` 這行孤零零掛在第二節末尾，看來原屬第三節。**第三節內容不明。**

### 9. 「當日新招標」與 16:10 排程互相矛盾

政府採購網整天都在上架公告，下午尤其多。16:10 執行等於**每天必然漏掉 16:10 之後公告的案子，且永遠不補**。

建議把查詢窗口改為「前一日 16:10 → 當日 16:10」，並保留已寄送紀錄避免重複。**但這需要跨日狀態，規格完全沒有這部分的設計。**

### 10. 更正公告的跨日重複

更正公告通常隔天才發。今天寄出更正版時，客戶昨天已經看過原公告了。目前決定「照寄並標註【更正】」，由客戶自行判斷。若要做到「只寄真正沒看過的」，同樣需要跨日的已寄送紀錄。

### 11. 範本本身的排除清單顯然是舊版

範本（2026-08-17）裡仍存在 `115學年度學生露營活動`、`115學年度二年級戶外教學露營活動採購案`、`高雄國家體育場戶外景觀坡地及步道區整護採購案` 這類案子——正是 38 條清單要擋的雜訊。**表示範本產出時間早於排除清單定案**。需與客戶確認：範本的其他部分（版型）是否也已過時。

### 12. 附件遞送

規格第七節：Scheduler MCP 的 xlsx 附件遞送待確認，fallback 為下載連結。**但核心目標明寫是「Email 一份 Excel」**，改成連結等於變更交付形式，且牽涉檔案存放位置、存取權限、連結有效期，規格均未著墨。建議不依賴該 connector，直接用 SMTP 寄附件。

### 13. 失敗時沒有通知路徑

`send_when_empty = True` 解決了「今天沒案子」的沉默，但**系統掛掉時連空信都寄不出去**。18:30 沒收到信，客戶無法分辨是「今天沒案子」還是「系統死了」。需要一條獨立的失敗通知路徑。

### 14. 單點依賴第三方 API

資料源是社群／基金會維運的服務，匿名呼叫有速率限制（實測約 10 次 / 7 秒即 429，且**無 `Retry-After` 標頭**）。建議向 openfun 申請 API token。服務中斷時的備援，規格未著墨。
