# 可行性評估：能不能用 Claude Code 的本機排程跑這條管線？

> 結論先講：**不行**。Claude Code 每一種本機排程機制都有一個致命條件不成立。
> 這條管線該用作業系統的排程器直接呼叫，中間不需要經過 Claude。
>
> 以下每一項都對照官方文件與工具本身的規格查證過。

## 需求是什麼

規格第五節：**每日 16:10 搜尋，18:30 前 Email**。

這是一個**截止時間**。而且這條管線裡沒有 LLM —— `select.js`、`enrich.js`、
`workbook.js` 全是純函式，89 條測試固定其行為。給定同一天的輸入，輸出必然相同。

這個性質很關鍵：**沒有任何需要「判斷」的環節**，所以也沒有讓模型參與的理由。

---

## 逐一檢驗

### 1. `/loop` — 在對話中重複執行

由 session 內的計時器驅動，Claude 閒置時在回合之間觸發。

**為什麼不行**：只在 Claude Code 執行中且閒置時才會觸發。終端機關掉、session 結束或
崩潰，就不再觸發。

**失效樣態**：16:10 時筆電在睡眠 → 不會執行，**也不會有任何錯誤**。等你發現時已經
漏了好幾天。

適合的用途：對話期間輪詢某個狀態（等 CI、等部署），不是每日排程。

### 2. `CronCreate` — session 內的 cron

工具規格本身寫得很清楚：

- **session-only、in-memory**，Claude 結束即消失，不寫入磁碟
- 只在 REPL 閒置時觸發
- 遞迴任務 **7 天後自動失效**
- 會加上抖動（遞迴任務最多延遲週期的 10%，上限 15 分鐘）
- `durable` 參數存在但**明文標示無效** —— 沒有持久化選項

**失效樣態**：關掉終端機，排程就沒了。而且就算不關，7 天後自動失效。

### 3. `/schedule`（cloud routines）— 唯一能持久的選項

這是**唯一**不需要你的機器開著的機制。每天 16:10 排得出來（最短間隔 1 小時的限制，
對「每日一次」不構成問題）。

**但它不是本機執行**：routines 跑在 Anthropic 管理的雲端，每次執行會**重新 clone
一份 repo**。所以：

- 產出的 xlsx 落在雲端的 clone 裡，**不會出現在你的磁碟上**
- 讀不到任何未 commit 的本機檔案 —— 包含刻意不進版控的收件人清單
- 需要 claude.ai 訂閱

要用它就得改設計：讓流程把檔案 commit 回 repo 或上傳到別處。技術上可行，
但那已經是另一套架構，不是「本機排程」。

### 4. Hooks — 沒有時間事件

hook 事件共 30 幾種（`SessionStart`、`PreToolUse`、`PostToolUse`、`FileChanged`、
`SessionEnd`…），**全部由使用者動作或 Claude Code 生命週期觸發，沒有任何一個是
時間驅動的**。

`Setup` hook 確實存在，但只在 `--init-only`、`-p --init`、`--maintenance` 時觸發，
是給 CI 初始化用的，不是排程。

（另外先前也查證過：**沒有安裝時的 hook**。`PostInstall`、`Install`、`PluginInstall`
都被判定為未知事件。所以 skill 帶的 `setup.sh` 不會自己執行。）

### 5. 自訂 slash command — 只有人能按下去

slash command 只在訊息開頭被辨識，也就是**只有人打字才會觸發**。排程、hook、
CLI 都無法把它當進入點。

### 6. `claude -p` headless — 可以，但轉了一圈又回到 OS 排程器

```bash
claude -p "產出今天的標案日報" --permission-mode dontAsk --allowedTools "Bash"
```

這是官方支援且有文件的用法，可以放進 cron / launchd。**但真正在排程的是 cron，
不是 Claude Code。** 而且多了兩個新的失效點：

- **憑證會過期**。`claude setup-token` 產生的長效 token 效期一年，到期後這個排程
  就開始失敗，需要人工更新。訂閱登入的憑證更短。
- 每次執行都要花 token 讓模型重新決定一件純函式早就決定好的事。

## 誠實的基準線：完全不用 Claude Code

macOS 用 launchd，Linux 用 cron：

```cron
10 16 * * 1-5  cd /path/to/gov-tender-monitor && npm run report
```

| | |
|---|---|
| 準時執行 | ✓ 由作業系統保證 |
| 檔案落在本機 | ✓ 直接寫進 `out/` |
| 失敗可偵測 | ✓ 非零 exit code |
| 憑證過期問題 | ✓ 沒有 |
| LLM 成本 | ✓ 零 |

唯一的前提是「那台機器在 16:10 是開著的」—— 而這個前提，上面每一種 Claude Code
的本機機制**同樣需要**，只是它們還額外要求終端機開著、session 活著、且在 7 天內。

## 那 Claude Code 在這件事上還有什麼用？

有，但不是在排程。是在**需要判斷的地方**：

- **「這個標案為什麼沒出現？」** —— 逐條檢查公告類型、採購性質、兩條命中路徑、
  38 條排除清單，然後指向 Excel 的「已排除」分區。這件事人做很煩，模型做很快。
- **判斷排除清單是不是訂太寬。** 「活動中心」擋掉了「台中市OO活動中心啟用晚會
  宣傳影片製作」—— 要看出這是誤殺，需要理解標的與場地的差別。這是判斷，不是規則。
- **臨時重跑、改規則、解讀異常。**

所以 skill 的定位是**臨時操作與問題排查的前門**，不是交付機制。這也是
`skills/gov-tender-monitor/SKILL.md` 裡明寫「不排程、不寄信」的原因。

## 一句話總結

> 排程要交給作業系統，判斷才交給模型。
> 這條管線是純函式，它需要的是一個準時的鬧鐘，不是一個會思考的助理。
