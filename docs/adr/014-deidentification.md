# 014. 去識別化只換客戶名稱，保留搜尋規則

**狀態**：已執行　**決策者**：使用者

## 背景

repo 要公開供課堂使用。盤點後，客戶相關資訊分兩類：

1. **身分**：客戶名稱與部門，出現在 4 個檔案。
2. **商業判斷**：`config/rules.json` 裡的 38 條排除清單、4 組關鍵字、4 個標的分類。
   規格第八節說那 38 條是「客戶回饋『這件不該出現』就加一條」累積出來的
   —— 等於客戶的選案標準，可能比名字更敏感。

## 決策

只代換身分。規則保留原樣。commit 歷史不重寫（demo 結束後刪除 repo）。

## 理由

規則是這個題目的核心。換成示意值的話，「規則實驗室」變成假的，
畢業紀念冊那個「排除清單推翻政府官方分類」的真實發現也就消失了 ——
課堂上最有價值的一幕沒了。

## 後果

- 4 處代換完成。

## 事後補記：代換過一次不代表乾淨

代換完成後，一個負責產出展示網頁的 subagent 在探索 repo 時（很可能是讀 git 歷史）
撈到了代換前的客戶名稱，並把它寫進網頁最上方的 eyebrow。這份網頁隨著另一個
commit 一起被 `git add -A` 提交並 push 到**已經公開的** repo。

發現方式：用 agent-browser 做視覺驗證時，在截圖第一行看到客戶名稱。
純文字檢查不會發現 —— 因為檢查是在網頁產出**之前**做的。

學到的是：**去識別化不是一次性的動作，而是一道每次產出後都要重跑的檢查。**
任何在代換之後新產生的檔案（尤其是由 subagent 產生、且會讀 git 歷史的）都必須重新掃。

處置：修正當前檔案後，**把整個 git 歷史壓成單一 commit** 並強制推送，
讓客戶名稱不再存在於這個 repo 的任何地方。原本的決定是「歷史不動，demo 完刪 repo」，
但那個決定是在假設「代換後的檔案是乾淨的」之下做的 —— 前提被推翻了，決定就跟著改。

反正這個 repo demo 結束就刪，歷史沒有保留價值。
- 自家公司的內部模組名稱（`tagtoo_xlsx.js`、`ad-report`）保留，那不是客戶資訊。
- README 加註說明這是課程作業、客戶已去識別化、資料來源為公開資料。
- **repo 在 demo 結束後刪除** —— 這是這個決策成立的前提。
