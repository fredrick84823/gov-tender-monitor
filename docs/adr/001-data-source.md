# 001. 資料源選用 openfun 鏡像 API，不自建爬蟲

**狀態**：已確認（事後補實驗）　**決策者**：使用者拍板，事後由實驗證實

## 背景

專案一開始面對三個選項：openfun 鏡像 API、自己爬官方採購網、先實測再決定。
使用者直接選了 API，**當時沒有做實驗**。

為了課堂說明與這則 ADR 的誠實性，事後補做了對照實驗
（`docs/experiments/api-vs-scraper.md`，10 筆真實標案、10 個欄位）。

## 決策

資料源使用 `https://pcc-api.openfun.app/api`。

## 實驗證據

### 爬蟲在絕大多數頁面上根本進不去

官方詳情頁有**撲克牌圖形驗證碼**，而且**無條件出現**，不是被速率觸發：
同一個 URL 以 6 秒間隔冷抓 5 次，**5 次全部被擋**。

10 筆樣本冷啟動只抓到 **2 筆**（那 2 筆是 `PPW-*` 參考資料公告，走另一條轉址、從未被擋）。

驗證碼**可解，是通行費而不是牆**：人工解一次之後約可連續看 6~7 頁，
credit 記在伺服器端、綁 IP，不在 cookie 裡。換算下來，`select()` 每天選出的 35 筆
需要**每天人工解 5~6 次驗證碼**。

而且 **WAF 硬擋 headless 瀏覽器** —— Playwright 在兩條路徑上都拿到
`Web Page Blocked! Attack ID: 20000051`，連搜尋首頁都被擋；
但同一時間、同一個 IP 用 curl 卻通得過。所以「開一個真瀏覽器去解驗證碼」
這條路在指紋層就被封掉了。

### 進得去的頁面上，兩邊的資料是一致的

8 筆可比對的標案、8 個招標類欄位：**84 組「兩邊都有」的欄位配對，語意差異 0 筆**。
在可觸及的範圍內，兩邊完整度打平（8/10 vs 8/10）。

這一點對爬蟲是有利的證據，必須寫進來 —— **鏡像沒有失真**。

### 但 API 在其他每一個軸上都贏

| 軸 | 勝方 | 數字 |
|---|---|---|
| 實際可觸及 | API | 冷啟動 10 筆抓到 2 筆 vs 10 筆 |
| 結構深度 | API | 79~88 個 detail 欄位 vs 65~66 個解析到的標籤；16~22 個只有 API 有（巢狀表格） |
| 值的可用格式 | API | `標的分類` **8/8 筆格式不同**，爬來的形式會讓 `parseCategory()` 回 `null` |
| 公告史 | API | 一次呼叫回傳 1~7 個版本；官網一個 URL 只有一版 |
| 資料來源時間 | API | 有 `fetched_at`，官網頁面完全沒有 |
| 延遲 | API | 中位數 **283ms** vs **1834ms**（6.5 倍）；回應 18.8KB vs 120.6KB |
| 程式碼量 | API | 取同樣 10 個欄位，**7 行 vs 98 行** |
| 第一手、無中介 | **爬蟲** | 這是爬蟲唯一勝出的軸 |

### 爬蟲獨有的欄位：零

官網有兩個標籤是 API 沒有的，但那兩個在 8 個頁面上**全部是空值** ——
官網會渲染空列，API 直接丟掉空值。其餘差異都是群組標題，API 編碼成 key 的前綴。

## 理由

不是「API 比較方便」，而是**爬蟲在這個需求下不可行**：

每日 35 筆需要 5~6 次人工解驗證碼，而需求是「每天 16:10 自動執行、18:30 前寄出」。
一個需要人工介入的步驟放在無人排程裡，等於這條需求不成立。

## 後果與代價

- **單點依賴一個非官方鏡像。** 鏡像掛掉或改版，整個系統停擺。已列入客戶問題清單
  （建議申請 API token、約定服務中斷時改寄「查詢失敗」通知）。
- 實驗證實鏡像**沒有失真**，這讓依賴的風險從「資料可能不對」降為「服務可能中斷」——
  後者是可監控、可備援的，前者不是。
- 官網頁面連結仍然有用：Excel 的超連結指向官網，讓人**手動**點開查證。
  人點得開（會遇到驗證碼但解得掉），機器抓不動 —— 這個分工剛好成立。

## 這則決策的後設觀察

決策先做、證據後補，順序是反的。事後補實驗有兩種可能結果：證實或推翻。
這次是證實，而且證據比原本預期的更強（原本以為差別在欄位完整度，
實際上差別在「能不能自動化」這個更根本的層次）。

但若當初實驗結果是推翻的，代價就是整個資料層重寫。**這個風險當時是真實存在的。**
